# scripts/gen_ref_pages.py

A simpler version of tradingmachine's generator: one page per module, the module as the title and each public class as a section in source order, plus tradingmachine's class hierarchy as the section's landing page. tradingmachine's example programs are left out, because trading-agent has no examples folder. It reads the source with `ast` and never imports the package, so the site builds without the project's dependencies, as the GitHub workflow does.

The class hierarchy page was first left out, and that emptied the left menu of the whole API reference. With only one package, the reference navigation had a single entry, `trading_agent`, whose `__init__.py` gives it an index page. With `navigation.indexes` on, Material takes a section's first child as the section's index when that child is an index page, so it used the package's page as the "API reference" link and hid the package's entry, and every module under it went with it. UBI never hit this because it documents three top-level packages. tradingmachine avoids it the same way as here: "Class hierarchy" is written first in SUMMARY.md, so it becomes the section's index and the package stays a visible, foldable section. Keep it first.

Base classes are resolved through the module's imports, so `order_tool.OrderTool` after `from trading_agent.tools import order_tool` becomes `trading_agent.tools.order_tool.OrderTool`. A class with exactly one base inside trading-agent hangs under it; any other class starts a branch with its outside bases named beside it.

An empty `__init__.py` gets no page, so a link to a package's index only works for packages whose `__init__.py` has a docstring, such as `trading_agent` itself. Packages with an empty `__init__.py` still appear in the menu as foldable sections without a page of their own.
